# 10 — Tool and command catalog

> **24 October 2026:** Information/confirmation requests now target text replies
> in the demo, not phone calls. The coordinator still proposes one typed action and
> scoped tools only read evidence. Simulated response input supplies evidence and
> wakes the coordinator; it does not bypass approvals or directly close repairs.

This is an application interface specification. Provider APIs are documented separately. Schemas from [06](06_DOMAIN_MODEL.md) are canonical. “Tool” does not mean every function is exposed to the coordinator.

## Authority boundaries

1. The coordinator receives a scoped snapshot and may call read tools.
2. It returns one `ActionProposal`; Pydantic validates its shape.
3. The policy layer checks version, evidence, allowed transition, authorization and outstanding effects.
4. The executor invokes a command; the command owns its database transaction and action/event records.
5. Provider requests happen outside that transaction, using the recorded action identity.

All mutation inputs require authenticated actor context and a caller-supplied idempotency key, supplied by trusted application code, not generated by the LLM. Case-scoped IDs are checked against the authenticated scope. Unknown external results are never treated as failure safe to retry.

Creating an event is a private transaction helper. There is no public `add_case_event` or generic `update_case_details` escape hatch. An actor cannot inject arbitrary lifecycle events.

`propose_next_action` is the model output, not an extra action tool. `rank_contractors` is a deterministic filter: approved trade match → service area → valid slot; tie-break by configured preference. ## ContractorConnector boundary

Interface operations: `list_slots(AppointmentQuery) → AppointmentOptions`, `book(BookingRequest) → BookingOutcome`, `cancel(provider_booking_id, idempotency_key) → CancellationOutcome`, `reconcile(action_id, provider_booking_id?) → BookingOutcome | CancellationOutcome`, selected by the recorded action kind.

Implement **MockBookingConnector only** for the hero workflow. It stores slot reservations in the same SQLite database so restart/duplicate tests are meaningful. The mock returns provenance SIMULATED and fictional booking IDs. `HumanDispatchConnector` may simply create a pending operator task. API, email and voice connectors are POST-HACKATHON; their existence as designs is not a claim that contractors expose those interfaces.

Rescheduling is confirmed cancellation followed by a new authorized booking with a new attempt ID. If cancellation is uncertain, do not place a second booking. Email sent, call started and message acknowledged are not booking confirmation.

## Idempotency and errors

Keys encode purpose and target, e.g. `report:{report_id}:prerequisite`, `booking:{work_order_id}:{slot_id}:{attempt}`. A repeated key with a different payload hash returns CONFLICT. A repeated identical request returns the existing result.

Version checking applies when admitting a fresh proposal. Approving an existing action is not a new model proposal: reload its immutable payload, validate the operator's current case version, recheck all business predicates, store approval and enqueue the same action ID. Revalidate again before send. The approval's own event/version increment must not make that action stale by mechanically comparing its original model snapshot version. Unrelated changed facts can still invalidate its scope/slot/evidence. Provider results for already-sent actions are ingested against the ledger even if case version changed; never discard a real acknowledgment as stale.

Common error codes: VALIDATION_ERROR, NOT_FOUND, FORBIDDEN, STALE_VERSION, POLICY_REJECTED, APPROVAL_REQUIRED, CONFLICT, RATE_LIMITED, PROVIDER_UNAVAILABLE, EXTERNAL_RESULT_UNKNOWN. Read-only transient requests may retry twice with jitter. A potentially committed effect transitions to UNKNOWN and reconciliation, never blind retry. All errors shown to the model are sanitized and bounded.

## Text demo and scheduling amendments — 24 October 2026

`POST /cases/{id}/demo-inputs` is outside the model tool surface. It supplies
SIMULATED evidence and one versioned coordinator wake; it never accepts/completes a
repair or bypasses an approval. See [16](16_API_AND_WEBHOOK_DESIGN.md) for its contract.
Both intake and replies reject unconfirmed, timezone-naive, expired, reversed or
unknown-timezone availability.

`find_appointment_options` checks case scope, approved contractor, required trade,
explicit postcode coverage and confirmed tenant windows. It returns only matching
simulated slots and an explanatory empty result otherwise. Returned identities are
remembered only within that model run; SCHEDULE_VISIT output validation rejects
uncited/invented options. Listing remains read-only.

Phone transport/routes and worker execution are removed. Historical phone-related
enums/columns remain readable for database compatibility. Historical pending call or
recording jobs fail closed with an explicit removed-feature error; they cannot dial.

## 24 October decision guard amendment

The static model tool contract is unchanged. Output validation requires all missing
safety questions, forbids repeated non-hazard triage, requires exact completion
report evidence, and rejects ambiguous equipment-as-NO_ACCESS decisions. Current
confirmed tenant access and READY/ACTIVE state are required to offer booking slots.
The contextual demo form adds explicit access withdrawal and operator-selected
concern resolution; these are audited evidence inputs, not new autonomous model powers.

## 24 October 2026 — Avoid duplicate evidence in model reads

`read_report`, `read_communication`, and entries returned by `list_case_events` may return a typed `SnapshotEvidenceReference` when the scoped database row exactly matches evidence already supplied in the current snapshot. It contains `status=ALREADY_IN_SNAPSHOT`, `record_id`, `snapshot_path`, and `additional_fields` for metadata omitted from the prompt projection. Older or changed records retain full responses. Case-scope checks and event pagination remain unchanged. This reduces repeated evidence without removing access to historical data. Input schemas and action validation are unchanged.

Mubit run diagnostics now retain numeric request/token/tool counts on failure and an allowlisted limit category; raw exception text, prompts, responses and secrets are not persisted in metrics. Limits are unchanged.

Tool preparation now omits a read only when its entire scoped DB collection exactly matches the snapshot and case versions match. Missing/truncated/changed evidence keeps the tool available. The prompt retains event authority and communication direction/timestamp metadata. Slot lookup and research access are unchanged. Limits remain bounded at the existing values.
